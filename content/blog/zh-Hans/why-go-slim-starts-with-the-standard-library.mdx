go-slim 是一组专注于 HTTP、数据处理与常用工具的 Go 类库。项目从一个简单的前提开始：抽象应该让重复出现的决策更容易完成，但不应拿走标准库原本清晰、可理解的行为。

## 类库应该解决一个决策

一个类库是否有用，不取决于它提供了多少函数，而取决于它能否帮助你反复做出一个具体决策。

- [`h3`](/zh-Hans/libraries/h3) 为 HTTP 应用提供路由树、中间件组合和明确的生命周期 owner，同时保留 `net/http` handler 与请求语义。
- [`binding`](/zh-Hans/libraries/binding) 将请求输入转换为类型化的应用数据，但不替领域决定这些数据的业务含义。
- [`nego`](/zh-Hans/libraries/nego) 根据 HTTP 协商规则选择响应表示，却不替你的 API 决定错误结构或渲染器。

这些包可以组合使用，但没有任何一个包强制依赖其他包。这是有意的设计：只负责一个边界的包更容易替换、测试和解释，也比一个接管整个应用的框架更容易逐步引入。

## 先从最小可运行形态开始

在引入类库之前，先让标准库版本的任务清晰可见。一个最小 HTTP 服务已经能够说明许多职责归属：

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, _ *http.Request) {
		fmt.Fprintln(w, "ok")
	})

	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

这个示例有意保持普通。当 go-slim 的某个包进入程序后，你仍然应该能看见请求在哪里匹配、响应在哪里写入，以及谁负责停止服务。类库应该减少重复的连接工作，而不是隐藏需要调试的行为。

## 把策略留在应用边界

类库可以提供机制，但策略仍然由应用决定。哪些字段有效、哪些凭证可信、哪些业务错误应该变成 `400` 或 `409`，以及应该向客户端返回哪种格式，都属于应用的职责。

这样的边界也让迁移更安全。你可以把一个包引入已有的 `net/http` 服务，保留现有 handler；如果将来的取舍不再适合，也可以替换这个包。代码通过标准接口连接，而不是绑定到某套私有框架词汇。

<Callout type="info" title="设计思想">
  优先选择可以在不重写应用的情况下移除的抽象。如果移除一个包就必须替换所有 handler、context 和 response type，那么这个边界可能放得太高了。
</Callout>

## 按路径阅读文档

文档也遵循同样的边界：

1. **概览**说明类库解决什么问题、什么时候适合使用，以及它有意不负责什么。
2. **指南**带你从安装走到第一个可观察结果，再按依赖关系增加常见任务。
3. **进阶**解释生命周期、并发、安全、性能，以及改变默认值需要承担的代价。
4. **示例**提供可以复制的应用形态，而不是孤立的 API 演示。
5. **AI**提供机器可读版本，方便工具搜索或将文档加载为上下文。

你可以从[类库目录](/zh-Hans/libraries)开始；如果正在构建 HTTP 服务，也可以直接阅读 [h3 指南](/zh-Hans/libraries/h3/guide)。

## 接下来会写什么

这份博客会记录项目中的设计决策：为什么一个包拥有现在的边界、实现遇到真实使用后发生了什么变化，以及哪些约束值得继续保持显式。版本说明会记录可以观察到的变化，工程文章则解释这些变化背后的原因。

如果你在使用某个包时发现边界不清晰，这正是有价值的反馈。提交 issue 时，请说明你要完成的任务、能够体现问题的最小示例，以及你期待的行为。清晰的问题，才能带来更清晰的 API。
