# Library 文档写作规范

这套文档首先帮助使用者完成工作，其次才解释包的组成。源码定义事实，文档负责把事实组织成可执行的使用路径。

## 1. 先定义读者任务

写作前用一句话回答：

> 读者读完这一页后，能在什么场景下完成什么结果？

如果一句话中只有类型、函数或功能列表，没有使用场景和结果，这一页还没有找到主题。

推荐标题：

- 创建第一个 HTTP 服务
- 安全读取请求体
- 为任务设置重试与 TTR
- 在反向代理后识别客户端 IP

不推荐标题：

- API 介绍
- 核心组件
- 功能列表
- 其他

API 名称可以作为标题，但只适合需要按名称定位的 reference 页面，例如 middleware 的 `BodyLimit`。

## 2. 按渐进层级组织

一个 library 根据复杂度选择下面的层级，不必为了形式创建空目录。

### 概览：帮助读者决定是否使用

概览必须回答：

1. 它解决什么具体问题？
2. 什么情况下适合，什么情况下不适合？
3. 最小成功示例是什么？
4. 使用者拥有哪部分职责？
5. 下一步该读哪一页？

概览不应展开完整 API，也不应以目录结构、类型关系或 feature list 开场。

### 指南：从第一次成功到常见任务

指南按依赖关系排列：

1. 安装并得到第一个可观察结果；
2. 完成最常见任务；
3. 加入错误处理；
4. 加入配置和组合；
5. 准备部署。

每一步只增加一个新概念。先给可工作的代码，再解释它为什么这样写。

### 进阶：解释取舍与失败边界

只有读者已经能正常使用后，才介绍：

- 生命周期与并发；
- 缓存、性能和资源上限；
- 一致性、恢复和降级；
- 安全与信任边界；
- 可扩展接口及其契约；
- 设计取舍和未解决的问题。

进阶页不重复快速开始，而应解释“为什么”“何时改变默认值”“改变后承担什么代价”。

### Reference：用于查找，不承担教学顺序

Reference 按 API 名称、配置字段或协议值组织，要求可扫描、完整、精确。它可以链接回指南，但不能代替指南。

## 3. 单页结构

任务型页面优先使用下面的顺序：

1. **结果句**：开头直接说明这一页帮助读者得到什么。
2. **适用条件**：必要时说明前置状态和不适用场景。
3. **最小示例**：只包含完成任务所需的代码。
4. **验证结果**：说明如何运行，以及正确结果是什么。
5. **逐步扩展**：错误、配置、组合和替代方案一次增加一项。
6. **设计思想**：紧邻产生选择的位置解释原因。
7. **注意事项**：说明真实失败模式，而不是笼统地说“请注意安全”。
8. **下一步**：给出自然的后续页面，不列无关链接。

Reference 页面可以改为：用途 → 最小调用 → 配置与默认值 → 错误语义 → 组合顺序 → 注意事项。

## 4. 解释设计思想的方式

设计说明要回答取舍，不要复述代码。

好的设计说明：

> `BodyLimit` 在已知 Content-Length 时可以提前拒绝；chunked 请求只能在读取时发现越界。因此 body consumer 仍必须检查读取错误。

不好的设计说明：

> `BodyLimit` 用于限制 body。

需要显眼提示时使用 Callout，并按语义选择类型：

```mdx
<Callout type="info" title="设计思想">
  解释为什么采用当前模型，以及它放弃了什么。
</Callout>

<Callout type="warning" title="注意">
  描述会导致错误结果、数据泄露或兼容问题的条件。
</Callout>

<Callout type="danger" title="安全边界">
  描述不可信输入、权限、secret 或不可恢复操作。
</Callout>
```

不要为了视觉效果滥用 Callout；普通限制直接写在相关段落。

## 5. 代码示例规范

- 示例以当前源码和测试为准，不从记忆猜测 API。
- 快速开始应能复制到一个最小程序中；省略代码时明确说明依赖的变量或 helper。
- 错误必须处理，除非示例正在单独说明成功路径并紧接着补充错误处理。
- 展示调用顺序、资源关闭和 context 传播。
- secret 使用环境变量或占位值，不写看似真实的凭证。
- 注释解释意图和边界，不逐行翻译代码。
- 不把 benchmark 数字、默认值或兼容版本写死，除非已从当前源码验证。

## 6. 使用者语言

- 以“你要完成的任务”组织，不以“包里有这些东西”组织。
- 首次出现术语时解释它在当前任务中的意义。
- 一段只表达一个判断；长枚举优先改为决策表。
- 中文保留必要的 Go/API 名称，但句子主体使用自然中文。
- 英文版与中文版保持事实、示例和页面结构一致，不做逐字硬译。
- 避免“简单地”“显然”“只需”等暗示读者不应遇到困难的表达。

## 7. 必须写清楚的边界

根据包的性质选择相关项：

- 缺失、空值、非法值分别如何处理；
- 错误在构造期、启动期还是请求期出现；
- 谁拥有资源，谁负责 Close/Stop/End；
- 是否可并发复用，哪些配置必须视为不可变；
- 是否读取或缓存 body，是否改变 request/response；
- 默认值、上限和无界模式；
- 重试、幂等、重复交付与部分成功；
- forwarded header、文件路径、模板和用户输入的信任边界；
- 进程内、单实例与分布式语义的区别；
- 该包有意不负责什么。

## 8. 双语与链接

- 两种语言必须拥有相同页面和相同渐进顺序。
- 英文默认路径使用 `/libraries/...`，中文使用 `/zh-Hans/libraries/...`。
- 重命名或移动页面前先搜索站内链接；能保留稳定 slug 时不随意改变。
- 页面标题可以面向任务，代码中的 API 名称保持原样。

## 9. Review checklist

提交前逐页检查：

- [ ] 开头两段是否说明使用场景和结果？
- [ ] 是否在第一次大段原理之前给出可工作的最小路径？
- [ ] 每个后续步骤是否只增加一个概念？
- [ ] 是否说明错误、资源、并发和安全边界？
- [ ] 设计说明是否解释取舍，而不是重复功能？
- [ ] 页面是否告诉读者什么时候不该使用当前能力？
- [ ] 所有 API、默认值和示例是否与当前源码一致？
- [ ] 中英文的事实和链接是否一致？
- [ ] 内容构建、类型检查和对应源码测试是否通过？

## 10. Library 状态

Library 可在 `_meta.yml` 中声明受约束的 `status`：

```yml
status: design
```

| 值 | 用户语义 | 展示 |
| --- | --- | --- |
| `design` | API 或实现仍在设计，不建议集成 | 设计中 / Design |
| `experimental` | 已可试用，但契约可能在无兼容保证下变更 | 实验性 / Experimental |
| `stable` | 可按已文档化契约正常使用 | 默认状态，导航中不显示 |
| `deprecated` | 仅为存量用户保留，新项目应选择替代方案 | 已弃用 / Deprecated |

未声明 `status` 时按 `stable` 处理。非稳定状态会在顶部 Library 导航和文档侧栏中展示；概览页仍必须用正文说明具体限制，不能只依赖状态标签。
