# Lifecycle

`App` combines a router, `http.Server`, and optional servlets. It also implements `Servlet`, so a larger process can own multiple app-like components with the same lifecycle shape.

## Start and stop

`Start(ctx)` performs startup work in order:

1. Build routes.
2. Create the TCP listener synchronously.
3. Start servlets.
4. Run HTTP or HTTPS in the background.

`Stop()` shuts down in the opposite direction:

1. Call `http.Server.Shutdown`.
2. Wait for in-flight requests.
3. Stop every servlet in reverse registration order.
4. Join shutdown errors into one returned error.

After `Stop` completes, the same app may be started again.

`Start` returns `h3: app is already started` when a run is active. Calling `Stop` before startup or after a completed stop returns nil. These methods still follow a single-owner, sequential contract; their return values do not make concurrent lifecycle calls safe.

## Options that affect serving

Common app options include:

| Option | Purpose |
| --- | --- |
| `Addr` | TCP address for the HTTP listener. |
| `Router` | Router to build and serve. |
| `Server` | Existing `http.Server` settings when the app should own the server lifecycle. |
| `TLSConfig` / certificate settings | HTTPS startup when the app should serve TLS directly. |
| `NotFound` | Handler for routing-layer 404 responses. |
| `MethodNotAllowed` | Handler for routing-layer 405 responses. |
| `OnStopped` | Callback after the HTTP service and servlets have stopped. |

Keep control-plane calls sequential. `Start` and `Stop` are lifecycle transitions, not request-path operations.

With an empty `Addr`, plain HTTP defaults to `:http` and a configured `TLSConfig` defaults to `:https`. `App.Start` validates the address and TLS certificate entry, builds routes, and opens the listener synchronously before starting servlets. Route grammar conflicts panic during `Build`; ordinary address, TLS, listener, context, and servlet startup failures are returned as errors.

## Startup context

The context passed to `Start` controls initialization, not the lifetime of every request. If the context is cancelled during startup, h3 closes the listener and rolls back successfully-started servlets.

A running app is finalized by `Stop` or by the HTTP service exiting. This avoids accidentally cancelling all requests just because an initialization context was cancelled later.

The base context for HTTP requests is owned by the current app run, not derived from the startup context. Normal request cancellation still follows `net/http` rules when clients disconnect or the server completes shutdown.

## Servlets

Use servlets for background resources that should start and stop with the HTTP app. This implementation is both repeat-stop safe and reusable across later app runs:

```go
type workerComponent struct {
	lifecycle sync.Mutex
	stop      chan struct{}
	wg        sync.WaitGroup
}

func (c *workerComponent) Start(ctx context.Context) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	c.lifecycle.Lock()
	defer c.lifecycle.Unlock()
	if c.stop != nil {
		return errors.New("worker is already started")
	}

	stop := make(chan struct{})
	c.stop = stop
	c.wg.Add(1)
	// The Start context controls startup checks and rollback only.
	// The worker receives a channel owned by this run.
	go func() {
		defer c.wg.Done()
		runWorker(stop)
	}()
	return nil
}

func (c *workerComponent) Stop() error {
	c.lifecycle.Lock()
	defer c.lifecycle.Unlock()
	if c.stop == nil {
		return nil
	}

	close(c.stop)
	c.wg.Wait()
	c.stop = nil
	return nil
}
```

Register a servlet without routes through `app.RegisterServlet(servlet)`. When a Component also implements `Servlet`, call only `app.Register(component)` and h3 enrolls its lifecycle automatically. Keep lifecycle transitions sequential; concurrent `Start` and `Stop` calls have no single correct order.

Do not pass the `Start` context to the long-running worker loop. That context controls startup checks and rollback only. Runtime shutdown should be driven by resources owned by the servlet, such as the per-run `stop` channel.

The servlet contract calls `Stop` once for each successful `Start`, but defensive components often make repeated cleanup safe because another owner may also call it. A permanent `sync.Once` is not sufficient for a restartable component: after the first run it cannot close the next run's channel. Reset state per run and wait for worker goroutines before returning from `Stop`.

## Rollback behavior

If startup fails after some servlets already started, h3 stops the successfully-started servlets and closes the listener. This avoids partially running applications where HTTP is unavailable but background workers remain alive.

`Stop` stops servlets in reverse order. Register dependencies before dependents when dependents should stop first.

Servlet lifecycle calls are protected with a panic boundary. A panic from `Start` becomes the startup error; a panic from `Stop` joins the other shutdown errors so remaining servlets are still stopped. During startup rollback, cleanup errors are logged and the original startup failure remains the returned error.

## Completion and errors

- Manual `Stop` returns the joined errors from HTTP shutdown, serving, and every servlet stop.
- An unexpected serving exit uses the same cleanup path and reports `manual=false` to `OnStopped`.
- Startup failures before a successful run do not call `OnStopped`.
- `Stop` waits for HTTP and servlet cleanup, but does not wait for `OnStopped` to return.
- `Run` waits until cleanup and the configured `OnStopped` callback have completed, then returns the run error.

## Shutdown limits

`Stop` intentionally has no context or timeout parameter. `http.Server.Shutdown` waits for active HTTP handlers, and servlet `Stop` methods run synchronously. Long-running handlers, streaming responses, and background loops therefore need an application-owned termination policy. Hijacked connections are not managed by `http.Server.Shutdown`; the component that hijacks them must track and close them.

## Response metadata

h3 can wrap responses to record the final status and size. Interim responses, hijacked connections, and advanced protocol details stay available through `Unwrap` and `http.ResponseController`.

Use this for access logs and tracing, but keep protocol-specific behavior in standard-library primitives.

Response metadata is final-response oriented. Advanced cases such as interim responses, `Flush`, `Hijack`, and protocol upgrades should still be handled with `http.ResponseController` or the unwrapped writer.
